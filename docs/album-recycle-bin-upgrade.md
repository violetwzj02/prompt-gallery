# 云端相册回收站：升级顺序与回滚

本功能拆成两份迁移，避免旧前端仍走「先删云盘、再删记录」时，数据库守卫先上线把元数据留下、原文件却已不可恢复。

## 迁移文件

1. 必选（加法，可先上）：`supabase/migrations/20261124115617_album_items_soft_delete.sql`  
   只增加 `deleted_at`、`deleted_by`、`purge_status`、`purge_error`、`drive_purged_at` 和部分索引，不改现有行，不改 RLS。现有条目读出来视为在架（`deleted_at` 为空，`purge_status` 为 `idle`）。
2. 可选（删除守卫，必须后上，本次不执行）：`docs/album-items-delete-guard.sql`  
   仅当 `purge_status = drive_purged` 时才允许删除 `album_items` 行。这份 SQL **不在** `supabase/migrations/` 中，避免 `supabase db push` 或默认迁移路径误执行。旧前端在云盘删除成功后仍会直接删行，若提前应用，记录会删不掉，而原文件可能已经没了。在无法证明所有旧客户端都已离线前，不要应用它。

两份文件都不得通过旧前端的硬删除路径来「兼容」；也不要添加 `public` 下的 `security definer` 捷径。

## 安全发布顺序（本次）

1. 加法迁移 `20261124115617_album_items_soft_delete.sql` 已在发布前端前手动应用到线上（现有 211 条记录保留，`deleted_at` 为空，`purge_status` 为 `idle`）。不要重复执行会改写现有行的语句。
2. 发布带回收站的前端。默认删除只把条目更新进回收站，不碰 Drive。若运行时发现列还不存在，前端会禁用删除/回收站并提示，**不会退回原来的硬删除**。
3. **本次不应用删除守卫。** 旧客户端尚未证明已全部离线。守卫 SQL 只作为文档保留，不进入默认迁移目录。
4. 等确认所有使用者都已刷新到新前端后，再由维护者手动执行 `docs/album-items-delete-guard.sql`。不要把它移回 `supabase/migrations/`，除非已经明确要纳入后续受控迁移。
5. 不要自动过期或自动清空回收站。不要在未确认的情况下执行任何删除。

## 回滚兼容

- 第 1 份迁移可以向后兼容旧前端（旧客户端忽略新列），因此回滚前端时，只要还没应用守卫，旧硬删除仍能删行。这是过渡期风险，不是原子保证。
- 一旦应用了第 2 份守卫，就不要把前端回退到旧硬删除版本。若必须回退前端，先撤销守卫触发器，再回退代码。
- 列可以保留；撤列不是回滚前端的必要步骤。
- 本仓库不会在发布前自动对线上数据库执行迁移。需要有权限的维护者按上述顺序手动应用。

## 运行时行为（前端）

- 查询隔离：在架 `live`（`deleted_at is null`）与回收站 `trash`（`deleted_at is not null`）。分类抽屉计数只统计在架条目。恢复后回到原来的分类。
- 默认删除：只 `UPDATE` 进入回收站，不调用 Drive。软删和恢复不要求已连接云盘。
- 永久删除只出现在回收站，且需要已连接 Drive。顺序为：标记 `pending` → Drive `DELETE`（HTTP 404 视为成功）→ 记录 `drive_purged` → 删除元数据。失败或中断可幂等重试；部分成功不得报成全部成功。云盘已删的条目不可恢复，重试只清理元数据。若云盘已删但数据库还没标上 `drive_purged`，下次重试会再走 Drive（404 成功）然后补标记并删记录。
- 上传失败时清理孤立云盘文件，与用户软删除不是同一条路径。
- 永久删除后按 `fileId` 逐张清缓存，不清空整个相册缓存。
